# Plan 03: OAuth 2.0 core (RFC 6749)

The authorization endpoint with Hydra-style login and consent challenges, the token endpoint, PKCE (RFC 7636),
refresh with rotation, and client credentials.

## Scope

| RFC 6749 section             | Status                                                                  |
| ---------------------------- | ----------------------------------------------------------------------- |
| §2.3 Client authentication   | `client_secret_basic`, `client_secret_post`, `none` with PKCE           |
| §3.1 Authorization endpoint  | GET and POST                                                            |
| §3.2 Token endpoint          | POST, `application/x-www-form-urlencoded`                               |
| §4.1 Authorization code      | Yes, with PKCE S256 required                                            |
| §4.2 Implicit                | No. `unsupported_response_type`                                         |
| §4.3 Password                | No. `unsupported_grant_type`                                            |
| §4.4 Client credentials      | Yes, confidential clients only, no refresh token (§4.4.3)               |
| §4.5 Extension grants        | No. The grant dispatch stays a table, so one can be added later         |
| §6 Refreshing                | Yes, with rotation and reuse detection                                  |
| §7 Accessing resources       | Bearer (RFC 6750). `api.verifyProviderAccessToken` for resource servers |

Also in scope: RFC 9207 (`iss` in the authorization response) and the parts of RFC 9700 listed under Security.

## Authorization endpoint

`GET /authorize`, and the same handler for `POST` (§3.1). One route, three entry modes, set by the query:

### Mode 1: a new request

1. Parse the parameters. A repeated parameter is `invalid_request` (§3.1). Parse with
   `c.req.queries()` and refuse any array longer than 1. Unknown parameters are ignored.
2. **Validate `client_id` and `redirect_uri` before anything else.** An unknown client, a `redirect_uri` that does not
   match, or a missing `redirect_uri` when the client has several, never redirects (§3.1.2.4, §4.1.2.1). They
   redirect to `ui.error?error=…`, or the app renders a minimal HTML error page when `ui.error` is absent.
3. From here on, every error redirects to the `redirect_uri` with `error`, `error_description`, `state` and `iss`:
   - `response_type` is not `code`: `unsupported_response_type`.
   - The client lacks `authorization_code` in `grant_types`: `unauthorized_client`.
   - `code_challenge` is missing, or `code_challenge_method` is not `S256`: `invalid_request`.
   - `scope` is unknown, or outside `client.scope`: `invalid_scope`. Without `scope`, the default is `client.scope`
     (§3.3 lets the server choose).
4. Store `idp/login/<challenge>` with the validated request. Generate a 32-byte CSRF value, store its hash in the
   record, and set it as an encrypted, `HttpOnly`, `Secure`, `SameSite=Lax` cookie scoped to the authorize path
   (`__Host-` prefix when there is no `basePath`).
5. Read the remembered-login cookie, when `durations.remember > 0`. When it names an Auth Dance session that still
   exists, mark the challenge `skip: true` with its identity.
6. Redirect 303 to `ui.login?login_challenge=<challenge>`.

### Mode 2: `?login_verifier=`

1. Load the login record the verifier points to. Check the CSRF cookie against its hash. A mismatch is
   `access_denied`. This step binds the browser that started the request to the browser that ends it, against
   login CSRF and session fixation (§10.12).
2. When the login was rejected, redirect to the client with its error.
3. When `client.skip_consent` is set, or `idp/consents/<identity>/<client>` covers the requested scopes, issue the
   code (Mode 3, step 3).
4. Otherwise store `idp/consent/<challenge>` and redirect 303 to `ui.consent?consent_challenge=<challenge>`.

### Mode 3: `?consent_verifier=`

1. Load the record, and check the CSRF cookie.
2. When consent was rejected, redirect with `access_denied`.
3. Create the grant (`gnt_`), and store `idp/code/<sha256(code)>` with a 60 s TTL. Delete the challenge records and
   clear the CSRF cookie. When the login asked for `remember`, set the remembered-login cookie.
4. Redirect 303 to `redirect_uri?code=…&state=…&iss=…`.

Every verifier is single-use. The challenge record flips a `verified` flag on first read.

## Challenge API

These are the in-process methods on `AuthDanceProviderApi`. The app mounts them as admin routes only when
`admin.authorize(c): boolean | Promise<boolean>` is given.

```ts
getLoginRequest(challenge): Promise<{
	challenge: string;
	client: AuthDanceRegisteredClientPublic; // no secret hash, no server-side fields
	requested_scope: string[];
	skip: boolean;
	subject?: string; // the identity id, when skip
	request_url: string;
}>;
acceptLoginRequest(challenge, options: {
	access_token?: string; // from the dance. Required unless skip.
	remember?: boolean;
}): Promise<{ redirect_to: string }>;
rejectLoginRequest(challenge, error: { error: "access_denied" | "login_required" | string; error_description?: string }):
	Promise<{ redirect_to: string }>;

getConsentRequest(challenge): Promise<{ challenge; client; requested_scope; subject: string; skip: boolean }>;
acceptConsentRequest(challenge, options: { grant_scope: string[]; remember?: boolean }): Promise<{ redirect_to: string }>;
rejectConsentRequest(challenge, error): Promise<{ redirect_to: string }>;
```

`acceptLoginRequest` calls `api.verifyAccessToken(access_token, { session: true })`. It takes `identityId`,
`sessionId` and `authTime` from the token, and nothing from the caller. A skipped login accepts with no token, and the
subject is the remembered one. `grant_scope` must be a subset of `requested_scope`. The client learns the result
through the `scope` member of the token response (§5.1).

Admin routes, under `/admin`:

```
GET  /admin/login?login_challenge=        PUT /admin/login/accept?login_challenge=     PUT /admin/login/reject?…
GET  /admin/consent?consent_challenge=    PUT /admin/consent/accept?consent_challenge= PUT /admin/consent/reject?…
```

## Token endpoint

`POST /token`. It accepts only `application/x-www-form-urlencoded`, and refuses a repeated parameter with
`invalid_request`. CORS is open to the origins of the registered `redirect_uris` of public clients, so an SPA can
call it.

### Client authentication (§2.3)

`src/idp/client-auth.ts` returns the authenticated client, or throws:

- `Authorization: Basic`: form-decode `client_id` and `client_secret` after base64 (§2.3.1, Appendix B).
- Body `client_id` + `client_secret`: only when the client is registered as `client_secret_post`.
- Body `client_id` alone: only for `none`.
- Two methods in one request (Basic and body secret): `invalid_request` (§2.3).
- The method used is not the registered method: `invalid_client`.
- Unknown client or wrong secret: `invalid_client` 401. Failures count against `address:client-auth:<address>`.

### `grant_type=authorization_code` (§4.1.3)

1. Hash `code` and load `idp/code/<hash>`. Missing or expired: `invalid_grant`.
2. `usedAt` already set: `invalid_grant`, **and revoke the grant** (§4.1.2, §10.5).
3. Set `usedAt` before minting anything, so two parallel exchanges cannot both pass. The KV has no compare-and-set.
   Document the race for eventually consistent stores (Cloudflare KV), and let an adapter offer `setIfAbsent` later.
4. The code belongs to another client: `invalid_grant`.
5. `redirect_uri` must be present and equal when the authorization request carried it (§4.1.3).
6. `code_verifier`: BASE64URL(SHA256(verifier)) must equal `code_challenge` (RFC 7636 §4.6). Verifier syntax
   43–128 chars of `[A-Za-z0-9-._~]`.
7. Mint the tokens.

### `grant_type=refresh_token` (§6)

1. The refresh token is `<gid>.<random>`. Load the grant, and compare `sha256(random)` with `refresh.current`.
2. It equals `refresh.previous` within `refresh_leeway`: `invalid_grant`, and the grant stays (a lost race). It equals
   `previous` after the leeway, or matches neither: `invalid_grant`, and the grant is revoked (RFC 9700 §4.14.2).
3. The grant belongs to another client: `invalid_grant`.
4. When the grant has a session, the session must still exist, or `invalid_grant`.
5. `scope`, when given, must be a subset of the grant's scopes (§6). A narrower scope applies to this access token
   only.
6. Rotate. A new refresh token goes to every client. For public clients the rotation is required, for confidential
   ones it costs nothing.

### `grant_type=client_credentials` (§4.4)

The client must be confidential and must have `client_credentials` in `grant_types`. Scopes are checked against
`client.scope`. The grant has no identity and no session. The access token has `sub = client_id`, and no refresh
token is issued.

### Token response (§5.1)

```json
{ "access_token": "…", "token_type": "Bearer", "expires_in": 300, "refresh_token": "gnt_….…", "scope": "a b" }
```

`scope` is always present, which is simpler than "present when it differs".

### Access token (RFC 9068)

Header `typ: at+jwt`, `kid`. Claims: `iss`, `sub` (identity id, or client id for client credentials), `aud` (the
client id by default, or a configured `audience` per client for a resource server), `client_id`, `scope`, `jti`,
`iat`, `exp`, `auth_time`, `gid`.

`AuthDanceProviderApi.verifyAccessToken(token, { grant?: boolean })` is for resource servers in process. It checks
the signature, `typ`, `iss`, `aud` and `exp`. With `grant: true` it also reads the grant, like `session: true` in the
core.

## Security (RFC 9700) checklist

- [ ] PKCE S256 for every client, `plain` refused.
- [ ] Exact `redirect_uri` match. Loopback port is the only exception.
- [ ] `iss` in every authorization response (RFC 9207).
- [ ] Codes are single-use, 60 s, hashed at rest, and reuse revokes the grant.
- [ ] Refresh rotation with reuse detection.
- [ ] No token in a URL except the code.
- [ ] `Cache-Control: no-store` on token responses.
- [ ] Redirects use 303, never 307, so a POST body never gets replayed (RFC 9700 §4.12).
- [ ] CSRF cookie binds each challenge to its browser.
- [ ] `X-Frame-Options: DENY` / `frame-ancestors 'none'` on the error page.
- [ ] Constant-time secret comparison.
